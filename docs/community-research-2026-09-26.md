# 从社区反馈到本轮迭代

研究核对日期：2026-09-26。以下是公开个案，不是用户总体统计。

| 原始来源 | 直接反馈 | 本项目的判断 |
| --- | --- | --- |
| [Langfuse #7333，2025-06-16](https://github.com/orgs/langfuse/discussions/7333) | Langflow 产生冗长 trace，检索片段埋在嵌套载荷里，逐组件定制代价高 | 先降低读取成本；这是从反馈到本地 CLI 的设计推断，不代表该用户验证了 AgentLens |
| [Langfuse #11953，2026-02-10](https://github.com/orgs/langfuse/discussions/11953) | 自托管用户报告升级后的历史数据/指标可见性问题 | 保持本地只读查看；报告根因未独立复现，不作竞品可靠性结论 |

现有替代：普通 inspect、JSON 搜索、Langfuse 等完整观测平台。本轮保留这些入口，只增加 `inspect --summary`，帮助先找到值得展开的事件 ID。没有证据支持另建托管平台、LLM 自动根因分析、更多仪表盘或完整执行回放。

实现边界：最多五条错误/失败信号、每条载荷预览 180 字符，run.failed 优先；完整 ID 保留。统计基于已记录事件，未记录结束不等于已失败；恢复错误仍计为历史信号，运行状态原样显示。Relay 证据与运行状态分开，归属与恢复未验证。无信号不证明健康。

验收：先运行新增 CLI 测试，确认缺少 --summary 时失败，再实现。Windows Node 24.13.0：lint、230 项测试、构建通过。覆盖错误定位、只读数据库 hash/mtime、确定性、互斥参数、恢复错误、未完成工具、大载荷截断和 passed + UNKNOWN。原 inspect/JSON/TUI 回归通过。

未验证：真实用户能节省多少定位时间、是否重复使用、是否优于其现有工具。下一轮优先根据公开问题和实际使用记录调整摘要内容；不把测试数当采用证据。
